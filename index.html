Services

What I can do for your contracts

Each engagement ends with artifacts your team keeps and can re-run: tests, scripts, a written report and a CI workflow. The work adds evidence about your contracts. It does not guarantee that they have no vulnerabilities.

  • Specification & Test Review

    A review of your contract against a written specification, to decide which properties need tests: access control, state transitions, accounting and reentrancy. Issues noticed along the way are reported, but this is test-focused work, not a full security audit.

  • Foundry Testing

    Deterministic unit and integration tests that map to specification properties, including boundary values, revert reasons and adversarial callback contracts.

  • Fuzzing

    Property-based fuzz tests over parameters and configurations with fixed seeds, so every run, and every failure, can be reproduced.

  • Invariant Testing

    Stateful handlers that run random sequences of actions and check system-wide properties such as fund conservation and solvency after every step.

  • CI Verification

    GitHub Actions workflows that pin the toolchain and run formatting, tests and coverage on every push. Mutation checks show which properties the tests actually enforce.

Case study

MilestoneEscrow

MilestoneEscrow is an ETH escrow for milestone-based work with a client, a contractor and a judge. It has submission, approval, dispute, arbitration, timeout refunds and pull-payment withdrawals. The case study pairs the contract with a written specification, four Foundry test suites and a verification report.

  • 45 tests passed, 0 failed, 0 skipped 34 deterministic · 8 fuzz (1,000 runs each) · 3 invariant (256 × depth 64)
  • 100% contract coverage Lines 98/98 · statements 141/141 · branches 28/28 · functions 13/13
  • 6 / 6 mutations detected Hand-written mutants, full suite per mutant, run locally
  • ✓ GitHub Actions succeeded Format, tests and coverage on a clean ubuntu-latest runner

What was tested

  • Cross-function reentrancy: receiver contracts call back into every lifecycle function during a withdrawal. A fuzzed equivalence property shows that a callback gives no more power than the same call made after the withdrawal.
  • Fund conservation: invariants check that total funding always equals unallocated funds plus credits plus withdrawals, and that the escrow balance covers what it still owes.
  • Constructor edge cases: each validation clause is tested on its own, including the maximum timestamps and arithmetic overflow at the boundaries.
  • Mutation check: six deliberate faults, such as removing the reentrancy guard or allowing a dispute at the exact end of the review window, each made at least one test fail.

Research lab

EIP-7702 and the “is the caller an EOA?” assumption

After EIP-7702, an externally owned account can install a delegation designator as its code. Checks such as code.length == 0 or tx.origin == msg.sender, long used to mean “this caller is a plain EOA”, no longer reliably mean that.

The eip7702-eoa-lab repository contains:

  • a shell script for a local Anvil chain that calls an “only-EOA” guard from the same account before and after a 7702 delegation;
  • a prototype pre-signing policy that checks a delegation target against an allowlist, the chain ID, code presence and the bytecode hash;
  • notes from a short manual review of four open-source account-abstraction projects for this pattern.

Status, stated plainly

  • This is a known class of assumption break, not a new vulnerability disclosure.
  • The repository publishes the scripts and a README. It has no CI workflow and no recorded run output, so this page reports no test results for it.
  • The review notes are the author’s own reading of public code. They are not audit findings.
  • The policy prototype only helps if it sits in a mandatory signing path, so it does not stop an attacker who already holds the private key.
  • Everything runs locally with public Anvil test keys and no real funds.

Methodology & Limitations

How the work is done, and what it does not prove

Methodology

  1. Specify. Write down roles, states, transitions and the properties that must always hold.
  2. Map. Link each property to at least one deterministic, fuzz or invariant test.
  3. Attack. Add adversarial actors such as reentrant receivers, recipients that reject payment and boundary timestamps.
  4. Challenge the tests. Inject faults by hand and confirm that the suite detects them.
  5. Reproduce. Pin the toolchain and seeds, keep the raw output and SHA-256 sums, and run everything in CI.
  6. Report. State the findings, the design decisions you accepted and the limits of the work.

Limitations

  • MilestoneEscrow is a portfolio project developed with AI assistance. Both the contract and the tests were produced that way and then reviewed and verified by the author.
  • It has not been independently audited. The verification report is a self-review.
  • It is not suitable for production and has never been deployed. Do not use it to hold real funds.
  • Coverage measures which code ran. It does not show that the code is secure.
  • The six mutants were chosen by hand. They are not a generated mutation campaign, and no mutation score is claimed.
  • No formal verification, gas study or testnet deployment rehearsal has been performed.
  • No engagement can guarantee that a contract is free of vulnerabilities. Independent audits remain recommended before you deploy anything that will hold value.
